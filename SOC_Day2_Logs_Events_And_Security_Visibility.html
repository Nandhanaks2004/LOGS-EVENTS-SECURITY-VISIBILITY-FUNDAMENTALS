Phase 1

The Invisible Evidence

Every action performed on a computer leaves traces. Even actions you think are gone forever are recorded somewhere. Let us prove it.

⚖ Scenario

The Windows Laptop Challenge

Imagine I hand you a Windows laptop. You perform these actions:

Login
Open Chrome
Visit Facebook
Download a File
Insert USB
Copy Data
Remove USB
Shutdown

Now I take the laptop. Can I prove you did those actions?

Most people answer "No." They are wrong.

Windows recorded almost everything you did. Every login, every program launch, every USB insertion, every shutdown — the operating system logged it. Even your visit to Facebook was recorded by Chrome's browsing history and possibly by network firewall logs.

You cannot perform a single action on a modern computer without leaving digital evidence. This evidence is stored in logs. And SOC analysts are trained to find and interpret this evidence.

Every Action Creates Evidence

User Login→Windows Records Event
USB Inserted→Windows Records Event
File Opened→Application Records Event
Website Visited→Browser Records Event
PowerShell Executed→Windows Records Event

Actions disappear. Evidence remains.

This single concept is the foundation of digital forensics and SOC investigations.

Phase 2

What Is a Log?

Before we talk about SIEM, detection, or alerts — we must understand the fundamental unit of security visibility: the log.

⚖ Analogy

The ATM Example

You walk to an ATM and withdraw ₹5,000. How does the bank know you withdrew that amount? How can they prove it? The answer is simple: the ATM creates a transaction record — a log.

ATM Transaction Log

Time: 10:45 AM
Account: 123456
ATM: ATM-001
Amount: ₹5,000
Status: Success

The bank uses this log to verify your transaction.

Cybersecurity Login Log

Time: 10:45 AM
Username: John
IP Address: 192.168.1.50
Action: Login
Status: Success

The SOC uses this log to verify user activity.

Log = Recorded Activity

Every time something happens on a system — a login, a file access, a network connection — a log entry is created. Logs are the paper trail of the digital world.

Phase 3

Why Logs Matter to a SOC Analyst

Logs are not just technical records. They are evidence. They answer questions. They tell stories. Let us see how SOC analysts use them every day.

👥 Scenario 1 — "I never logged into that server."

An employee denies accessing a critical server. How do you verify their claim?

Answer: Check the login logs. If the security log shows Event ID 4624 (successful login) with their username, timestamp, and source IP — the log proves the access happened, even if the employee denies it. Logs do not lie (unless tampered with).
🔍 Scenario 2 — "Who deleted this critical file?"

A shared file was deleted. Everyone denies doing it. How do you find the truth?

Answer: Check the file auditing logs or Windows Security log. The system records who accessed, modified, or deleted files. The event will show the exact username, process, and timestamp of the deletion.
🚨 Scenario 3 — Sensitive customer data was stolen.

A data breach occurred. Customer records were exfiltrated. Where do you start the investigation?

Answer: Logs tell the entire story. Start with: Who accessed the sensitive data? (database logs). When was it accessed? (timestamps). From where? (IP addresses). How was it transferred? (network logs). What commands were run? (PowerShell/process logs). Logs connect every piece of the puzzle.

Phase 4

Types of Logs

Not all logs are the same. Different systems generate different types of logs. SOC analysts need to understand each type and what it reveals.

⚙ System Logs

Generated by the Operating System
• Boot events • Shutdown events • Service start/stop • User login • User logout

Records OS-level activity. Shows when the system was running and which services were active.

🛡 Security Logs

Most Important for SOC Analysis
• Login success • Login failure • Password change • Privilege escalation • Account lockout

Primary focus for SOC analysts. These logs reveal authentication and authorization activity.

💻 Application Logs

Generated by Software Applications
• Web server access • Database queries • Application errors • API calls • User actions

Show what users and processes are doing inside specific applications.

🔗 Network Logs

Generated by Network Devices
• Source IP • Destination IP • Port and protocol • Blocked connections • Traffic volume

Track network communication. Essential for identifying unauthorized connections and data exfiltration.

⚙ Classroom Simulation

Which log would show a failed login?

Think about it before clicking. This is the kind of question a SOC team lead might ask a new analyst.

Answer: Security Logs. A failed login (Event ID 4625 in Windows) is recorded in the Security log. This is the most important log category for SOC analysts because it contains authentication events — who tried to log in, when, and whether they succeeded or failed.

Phase 6

Linux Logs

Linux servers power most of the internet. Understanding Linux logging is critical because attackers frequently target Linux infrastructure.

💻 Lab 2 — Linux Authentication Logs

Where Linux Stores Logs

Unlike Windows which uses a graphical Event Viewer, Linux stores logs as plain text files in the /var/log directory.

Navigate to Log Directory

$ cd /var/log
$ ls
auth.log syslog kern.log messages apache2/

Key files: auth.log (authentication), syslog (system), kern.log (kernel)

View Authentication Log

$ sudo less /var/log/auth.log

Scroll through the file to see login attempts, sudo commands, and authentication failures.

Examining Linux Authentication Events

Search SSH Events

$ sudo grep sshd /var/log/auth.log
Jun 9 09:15:22 server sshd[1234]: Accepted password for john from 192.168.1.50 port 22
Jun 9 09:18:44 server sshd[5678]: Failed password for admin from 203.0.113.50 port 22

Identify successful and failed SSH authentication attempts.

Real-Time Log Monitoring

$ sudo tail -f /var/log/auth.log

This command shows new log entries in real-time.

Try this:
1. Open a terminal with sudo tail -f /var/log/auth.log
2. In another terminal, SSH to the system
3. Watch new log entries appear in real-time

Phase 7

Normal vs Suspicious Logs

This is one of the most important skills a SOC analyst develops — the ability to distinguish normal activity from suspicious activity.

Practice: Normal or Suspicious?

Read each scenario and decide whether the log entry represents normal activity or a potential security threat.

Scenario 1: A single failed login attempt for user "john" at 10:00 AM from the office IP range (192.168.1.x).
Correct — Normal. A single failed login is common. The user may have mistyped their password. SOC analysts look for patterns, not isolated events.
Scenario 2: 50 failed login attempts for user "admin" from IP 203.0.113.50 within 2 minutes (Event ID 4625 in Windows Security Log).
Correct — Suspicious. 50 failed attempts in 2 minutes is a classic brute-force attack pattern. The attacker is trying to guess the password by trying many combinations rapidly.
Scenario 3: User "john" logs in at 10:00 AM from IP 192.168.1.50 (office IP). Event ID 4624.
Correct — Normal. This is John logging in from the office during business hours. The IP matches the company's internal range. This is expected behavior.
Scenario 4: User "john" logs in at 3:00 AM from IP 85.17.23.45 (located in Russia). John works in the New York office. Event ID 4624.
Correct — Suspicious. John logging in at 3:00 AM from Russia while working in New York is highly abnormal. This could indicate credential theft — someone else is using John's account from a different location.

Logs Are Meaningless Without Context

A single log entry is just data. It is the context — the time, location, frequency, and patterns — that transforms data into evidence. This is the most important mindset shift for new SOC analysts.

Key Interface Elements

Search Bar

Where analysts type queries to find specific log data. Think of it as a search engine for your security logs.

📅
Time Picker

Select the time range for your search. Critical for narrowing investigations to specific time windows.

💻
Hosts

Shows which systems (servers, workstations, devices) are sending data to Splunk. Each host is a data source.

📦
Sources

Specific log files or data inputs being monitored — like /var/log/auth.log, Windows Security Log, or Apache access logs.

Categories that define how Splunk interprets log data. For example: WinEventLog:Security, linux_secure, or access_combined.

Pre-built visualizations that give SOC analysts at-a-glance visibility into security events, trends, and anomalies.

Knowledge Check

Test Your Understanding

These questions test your understanding of logs, events, evidence, and the role of SIEM in SOC operations.

1. Why are logs important in cybersecurity?

Correct! Logs capture every action performed on a system — logins, file access, network connections, process execution. They serve as the digital evidence trail that SOC analysts follow during investigations.

2. What makes a log entry become evidence?

Correct! A log becomes evidence when it contains actionable information — a timestamp, a username, an action, a source, and a result. Without these details, a log is just data. With them, it becomes evidence.

3. Can a single log entry prove an attack?

Correct! A single failed login could be a user mistyping their password. But 50 failed logins from a foreign IP in 2 minutes — that is evidence of a brute-force attack. Context is everything in log analysis.

4. What is the difference between a System Log and a Security Log in Windows?

Correct! System Logs track OS operations like driver loads and service crashes. Security Logs track who logged in, when, and whether they succeeded — this is the primary focus for SOC analysts.

5. Why do organizations use a SIEM instead of manually reviewing logs?

Correct! A single firewall generates 20,000 logs per hour. An enterprise with hundreds of devices produces millions of log entries daily. No human can review this volume. SIEM platforms collect, index, and correlate this data so analysts can find threats quickly.

6. What is Windows Event ID 4624?

Correct! Event ID 4624 means a successful logon. SOC analysts monitor 4624 events to track who is logging in, from where, and at what time. An unexpected 4624 at 3 AM from a foreign country is a major red flag.

7. What is Windows Event ID 4625?

Correct! Event ID 4625 indicates a failed login. A few are normal (typos), but hundreds in minutes indicate a brute-force attack in progress. This is one of the most common alerts SOC analysts investigate.

8. Why is context important when analyzing logs?

Correct! "User John logged in" means nothing without context. John logging in at 10 AM from the office is normal. John logging in at 3 AM from Russia is suspicious. The same event, different context — different conclusion.

9. Why can't SOC analysts manually review all logs in an enterprise?

Correct! A single Windows server generates 5,000 events per hour. An enterprise with 100 servers, firewalls, and endpoints generates millions of events daily. No human team can manually review this volume — which is why SIEM automation is essential.

10. What problem does a SIEM solve for SOC analysts?

Correct! A SIEM transforms the impossible task of reviewing millions of logs into manageable investigations. It collects logs from everywhere, indexes them for fast search, connects related events, and alerts analysts only when something requires attention.
